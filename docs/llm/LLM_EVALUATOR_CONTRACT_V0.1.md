# LLM Evaluator Contract V0.1

Status: FROZEN

## Purpose

Add an independent semantic evaluator alongside the existing deterministic evaluator. The LLM is initially shadow-only. It must understand the actual vacancy text and candidate profile, not imitate the rule-based evaluator.

## Core principle

Recall > Precision.

The primary value of the LLM evaluator is to detect relevant roles that deterministic rules may under-rank or miss because of title variation, interdisciplinary wording, transferable methods, indirect domain fit, or nuanced eligibility language.

## Independence rule

The LLM must make its judgment without seeing any current rule-based decision, score, tier, recommendation, reason, keyword hit list, or evaluator-specific feature vector.

Rule-based output may be joined only after the LLM response has been produced and validated, for shadow comparison and disagreement analysis.

## Evidence hierarchy

The model must reason from vacancy evidence in this order:

1. Full job description and requirements text.
2. Responsibilities, essential criteria, desirable criteria, and other source text if separately available.
3. Title, institution, location, contract and seniority metadata.
4. Candidate profile supplied as a separately versioned artifact.

Structured metadata is supporting evidence. It must never replace the full vacancy text when the full text is available.

No keyword-only summary, rule-derived score, or hand-built feature set may be used as a substitute for the source vacancy text.

## Input contract

Schema: `schemas/llm_evaluator_input.schema.json`

Schema version: `LLM_EVALUATOR_INPUT_V0.1`

Required job evidence:

- stable job identifier
- title
- institution
- location
- detail status
- full vacancy text field
- candidate profile version

Optional supporting evidence includes country, contract type, seniority, responsibilities, essential criteria, desirable criteria and source URL.

The input contract intentionally does not contain fields for rule-based decision, rule-based score, rule-based tier, rule-based reason, keyword match flags or deterministic evaluator dimensions.

## Missing or degraded job text

The evaluator must still be able to return a valid result when source text is degraded, but it must explicitly represent lower evidence quality and avoid high-confidence semantic conclusions unsupported by the available text.

`evidence_quality` must be one of:

- `FULL_JD`
- `PARTIAL_JD`
- `LIMITED`
- `INSUFFICIENT`

A later implementation stage may define exact confidence caps for degraded evidence. L0 does not set those thresholds.

## Output contract

Schema: `schemas/llm_evaluation.schema.json`

Schema version: `LLM_EVALUATION_V0.1`

Required output:

- `decision`: `STRONG_APPLY`, `APPLY`, `REVIEW`, or `SKIP`
- `fit_score`: 0-100
- `confidence`: 0-100
- `domain_fit`: 0-100
- `methods_fit`: 0-100
- `seniority_fit`: 0-100
- `eligibility_risk`: `NONE`, `LOW`, `MEDIUM`, `HIGH`, or `UNKNOWN`
- `transferable_fit`: 0-100
- `hard_blocker`: boolean
- `hard_blocker_reason`: string or null
- `reason_short`: concise evidence-based rationale
- `evidence_quality`

If `hard_blocker=true`, `hard_blocker_reason` must be non-empty.

## Semantic expectations

The LLM is expected to distinguish between:

- mandatory and preferred requirements
- exact-domain fit and adjacent-domain fit
- direct experience and genuinely transferable methods
- title mismatch and actual responsibility match
- seniority mismatch and merely unusual job naming
- legal or credential blockers and soft preferences
- a role that is scientifically adjacent but realistic versus a superficially similar but irrelevant role

The evaluator should use the candidate's broader capabilities when justified by the text, rather than requiring exact keyword overlap.

## Shadow-mode authority

L0 freezes the following authority rules for the first implementation:

- The deterministic evaluator remains authoritative for production output.
- The LLM cannot auto-promote, auto-demote, delete, hide or rewrite a production recommendation.
- The LLM result is stored separately.
- Comparison happens only after independent LLM evaluation.
- Disagreements are evidence for later human review and calibration.

## Prohibited inputs in the initial LLM prompt

The following must not be exposed to the model before it returns its independent evaluation:

- current rule-based decision
- current rule-based recommendation
- current rule-based score
- current evaluator tier
- deterministic reason strings
- positive/negative keyword hit lists generated by evaluator rules
- any field whose purpose is to tell the LLM what the existing evaluator concluded

Raw vacancy text may naturally contain words that are also used by deterministic rules; that is not prohibited.

## Candidate profile boundary

The actual candidate profile is intentionally not frozen in L0. It is the deliverable of L1 and must be versioned independently.

L0 only freezes the requirement that every LLM evaluation identifies the candidate profile version used.

## Model boundary

L0 is model-agnostic. It does not select a vendor, model, token budget, batching strategy or API pricing plan.

Those decisions belong to later implementation stages and must not alter this semantic contract without a version change.

## Change control

Any later change that exposes rule-based conclusions to the LLM before evaluation, removes source-text-first reasoning, changes decision labels, or changes required output semantics requires a new contract version.
